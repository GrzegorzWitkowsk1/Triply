## Root cause and failing reproduction

`confirmTripRequirements` validated a previously loaded Mongoose document, assigned its confirmation fields, normalized its old malformed `analysis.location` to `null`, and called `trip.save()` inside `guestWrite`.

Mongoose saves dirty paths rather than replacing every field, but those writes had no current-requirements CAS. The normalization made `analysis.location` a dirty path. A requirements edit through `saveTripRequirements` could repair the coordinates after the confirmation snapshot was loaded; its `findOneAndUpdate` did not advance Mongoose's `__v` in a way that protected the later save. The old confirmation could then persist `null` over that repair. The guest transaction fenced migration, but did not make the old requirements snapshot current.

The permanent regression in `apps/api/src/services/tripDraft.confirmation.test.ts` follows the exact reported interleaving:

1. Create an owned complete Paris draft in disposable MongoDB. Use the raw collection to model malformed legacy coordinates `{lat: 999, lng: 2.35}`.
2. Load confirmation snapshot A.
3. Load snapshot B and call the real `saveTripRequirements` service with Rome, Italy and `{lat: 41.9, lng: 12.5}`. Assert the repair succeeded.
4. Call the real `confirmTripRequirements(A)`.
5. Assert the Rome coordinates and complete repaired persisted state survive, and stale confirmation returns an exposed 409.

Before the production change, the test failed at the coordinate-preservation assertion: **expected `{lat: 41.9, lng: 12.5}`, received `null`**. This is the original application defect, not a synthetic failed mock expectation. Provider functions were mocked, unexpected `fetch` calls threw, and only an owned disposable replica set was used.

## Persistence strategy and conflict behavior

The existing shared analysis parsing and `missingFields` validation remain first. An incomplete confirmation still raises `TripRequirementsIncompleteError`; the route retains its HTTP 400/missing-fields contract.

For otherwise complete requirements:

1. Derive the existing owner filter from the loaded document and read a raw owned snapshot. Reject a missing document or changed status with a controlled 409.
2. Hydrate that raw snapshot and compare its `analysis`, `confirmedFields` and `missingFields` with the caller's plain snapshot using Node's `isDeepStrictEqual`. This detects requirements that changed before the new read, including the original F-01 race. Hydration allows legacy missing fields and Mongoose defaults to be compared consistently.
3. Execute `findOneAndUpdate` inside the unchanged `guestWrite` transaction boundary. Its predicates include `_id`, the account/guest owner filter, the caller's exact status and `$expr` comparisons of all three raw persisted fields from step 1. `$literal` preserves their raw shape without query casting/default insertion; `$ifNull` handles absent/null fields in the same pattern as the existing attraction backfill.
4. Set only `confirmedFields`, `missingFields` and `analysis.location`. The latter retains existing legacy coordinate normalization. Return the fresh updated document, with validators enabled and the guest transaction session attached. There is no upsert.
5. If the atomic update matches nothing, throw the existing exposed conflict error **inside** `guestWrite`, before transaction commit.

Both stale-snapshot detection and a losing atomic update use the message: `The trip changed while confirming. Reload it and try again.` The existing HTTP error handler exposes it as 409. A document missing at the route's initial lookup retains its existing 404; deletion/ownership change after a snapshot was loaded becomes a conflict without returning another owner's data.

The CAS does not depend on `updatedAt` or `__v`: same-millisecond requirements changes are covered, while unrelated attraction enrichment or budget updates need not invalidate confirmation. Status must still match exactly; confirmation changes no status or generation metadata. Current ready-trip confirmation remains supported, as before. Two simultaneous confirmations from the same initial unconfirmed state produce one success and a controlled losing conflict. A fresh confirmation of already-current confirmed state remains supported.

There is no automatic reload-and-confirm of changed choices. The caller must reload after a conflict. Unrelated dirty fields on the input document cannot be persisted through this function.

## Guest transaction compatibility

No guest lease, migration, session or transaction implementation changed. The atomic update is executed through `guestWrite` with its supplied session, preserving the handoff write and resource update in one transaction. Account calls retain the existing non-guest path.

The implementation reuses `GuestActivityError` with a confirmation-specific message because `guestWrite` already preserves this exposed 409 type. Throwing a generic error inside that wrapper would convert it to a safe 503. Throwing only after returning a null update would allow the handoff revision to commit despite rejection; the new code instead throws before commit, rolling that revision back.

Regression evidence includes:

- Pause a real guest HTTP confirmation before the durable fence check, register its account, observe migration busy, expire only the disposable fixture's lease, complete real migration, then resume confirmation. The old request returns 409, the imported trip and completed handoff remain unchanged, and account ownership is retained.
- Pause a guest confirmation before the native resource write, change requirements through the real service, then resume. The old transaction retries/conflicts safely, returns 409 and leaves no confirmation or handoff revision committed. The intervening service call is fixture-driven outside a request context to create the controlled persisted interleaving; it is not a new application bypass.
- Inject failure after the native confirmation update executes within its transaction. The HTTP result is 503 and both the trip update and handoff revision roll back.
- Successful guest confirmation commits one handoff revision and returns the existing detail contract. Incomplete confirmation returns 400 without altering the trip or incrementing the fence.

Tests synchronize with deferred promises at explicit persistence/provider boundaries. They use no arbitrary sleeps, persistent database or live provider. Lease expiry is controlled only in the disposable fixture.

## Remaining risks and limits

- Confirmation adds one owned snapshot read before its atomic write. The read is not a lock; the database CAS remains authoritative. A competing change can legitimately produce 409 and require reload. Unrelated Budget/enrichment state is returned from the updated document rather than the stale caller.
- The guard compares the whole analysis and confirmation arrays, so a changed requirement, including notes or array order, conservatively invalidates confirmation. It intentionally does not merge or infer user approval of changed inputs.
- Guest writes still require a transaction-capable MongoDB deployment, and safe rollout still requires compatible workers. This fix does not activate the existing development replica-set/loopback configuration or resolve its recorded operational blockers.
- Tests use a real disposable single-node replica set with deterministic boundaries. They establish database state and transaction rollback under these interleavings, not independent OS-process crash or production-load behavior.
- The original final verification report remains an unchanged historical record. Its F-01 code defect is addressed by this report; its other findings, disabled Assistant and separate adversarial AI/external API audit remain outside this task.
