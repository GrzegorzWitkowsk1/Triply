## Root causes

**#22A-02:** Full generation applied the planning limiter only to guests. Authenticated users could generate different drafts concurrently. The per-trip claim protected one trip, not the account. Existing limiter counters live in `FixedWindowStore` Maps, so each API process had independent allowances. Location search accepted unbounded/repeated query parameters and had no route admission. Identical-query single-flight reduced duplicate lookups but did nothing for distinct queries. Authenticated destination recovery could call geocoding before claiming generation.

**#22A-06:** A generating trip was considered abandoned after two minutes based on `generation.startedAt`. Weather, attraction failover, Geoapify, sequential daily routing and opening-hours replanning can exceed that. No overall execution deadline stopped the original worker. Start-time predicates prevented some replacement overwrites, but a worker could commit after the supposed abandonment threshold if nobody replaced it.

Before changing implementation, two tests in `trips.routes.test.ts` reproduced both failures: a competitor acquired a claim after 130 seconds, and an expired worker persisted an itinerary after 241 seconds. That baseline run had **35 passing / 2 failing** tests.

## Investigated lifecycle

1. Fastify checks origin, parses bounded JSON, resolves the Mongo-backed signed session, then applies private route identity hooks. Missing identity receives the existing authentication/session rejection; caller-supplied user/guest fields are never admission identities.
2. Guest identity acquires the existing five-minute activity lease. Existing guest network and applicable planning limits run in preHandlers. The new admission handler wraps only analysis, full generation and location search, including automatic location HEAD routes.
3. Shared admission completes before handlers can call providers, reserve a guest generation allowance, or reserve Geoapify credits. Malformed or inaccessible requests may consume a request-window entry, but never generation quota or provider credits merely because they were admitted.
4. `/trips/analyze` can invoke AI, geocoding, weather and attraction discovery while upserting a draft. It shares generation admission and concurrency. Existing guest draft-slot reservation and failure cleanup remain intact. Analysis retains its existing quota policy.
5. Full generation validates ownership, requirements and guest duration. Authenticated draft destination recovery remains before the trip claim, but is now inside account admission and cancellation. An authenticated abandoned `generating` trip is reclaimed before coordinate recovery, so recovery has fresh write authority. Guest generation retains quota reservation → trip claim → quota `start()` → destination recovery. A rejected claim removes the unused quota reservation.
6. Claims atomically acquire a fresh UUID and expiry. Full generation itself does not call AI; AI analysis is the separate endpoint above.
7. Weather retains its cache, horizon, timeout and optional failure behavior. Attraction discovery retains per-trip freshness, sequential Overpass retries/failover, Retry-After handling, valid-empty behavior and metered Geoapify fallback.
8. Deterministic clustering, scheduling, sequential routing and opening-hours improvement run under the same execution context. Provider timeouts and pacing remain separate from the overall deadline. Optional routing failure still produces approximation.
9. Quality/repair and expense-link calculation precede narrow generation persistence. Owner, status, UUID, start time, expiry and existing budget revision predicates protect the write. Existing itinerary revisions and expense-link retries remain intact.
10. Guest persistence still runs inside `guestWrite`: lease/handoff validation and the resource write are in the same transaction. Cancellation is checked again inside the write callback, after the guest fence, including transaction retries.
11. Success, provider failure and cancellation settle the handler before removing its admission token. A process crash leaves expiring admission/claim state; a later request can recover it without a cleanup job. Late releases remove only their own token, and late generation results cannot overwrite a replacement.

## Admission policy

| Operation | Shared request window | Shared concurrent work | Execution budget |
| --- | --- | --- | --- |
| Analysis and full generation combined | 20 admitted attempts / 10 minutes / owner | 1 combined operation / owner, across all drafts and both endpoints | At most 240 seconds from admission |
| Location search, GET and HEAD | 30 admitted attempts / minute / owner | 4 operations / owner | At most 10 seconds; geocoding transport retains its 5-second timeout |

Configuration: `GENERATION_REQUESTS_PER_10M` (default 20) and `LOCATION_REQUESTS_PER_MINUTE` (default 30), validated positive integers up to 1000. Concurrency and execution budgets are explicit policy constants rather than independently adjustable lease durations.

The generation window preserves the existing 20-per-ten-minute planning envelope while extending durable enforcement to authenticated full generation and analysis. One operation allows normal sequential planning/retry while preventing one account from fanning out across drafts. Thirty searches per minute permits interactive location selection; four simultaneous requests accommodates overlapping UI queries without unbounded distinct-query traffic. The four-minute generation budget accommodates work beyond the old two-minute threshold and remains below guest authority. These are initial limits, not production capacity measurements.

Identity keys are operation scope plus the authenticated account ID or server-resolved `guest:<id>`. No request body, query identity, forwarded user header or trip ID can change the account partition. These private keys and lease/run IDs are never returned. No anonymous/IP fallback is needed: these routes already require an authenticated account or a valid guest session. Existing guest network controls remain supplemental.

`resource_admission` stores one document per scope/owner, using its built-in unique `_id`. Atomic MongoDB predicates and update pipelines enforce both the window and live token count. Writes use majority acknowledgement with a five-second write-concern timeout. Fixed windows start with the first admitted attempt after expiry. Concurrency/rate rejections do not increment the admitted counter. Completed, failed and invalid admitted attempts retain their window count. Expired tokens are filtered during acquisition; TTL is only storage cleanup. Database errors fail closed before provider work. There is no queue.

Rate rejection: HTTP **429**, `RESOURCE_RATE_LIMITED`. Concurrent-work rejection: HTTP **409**, `TOO_MANY_CONCURRENT_OPERATIONS`. Both include finite `Retry-After` seconds. The client should wait, reload current trip state, then retry. Changing trip or idempotency key does not evade the owner gate. A normal completed itinerary retains its existing idempotent response, subject to admission.

Location validation accepts one trimmed `q` string of 2–120 characters, rejects control characters and repeated query parameters, and returns **400 / INVALID_LOCATION_QUERY** before geocoding. Existing shared analysis constraints remain: 2,000-character prompt, 100 KiB JSON body, at most 365 trip days; guests remain limited to their configured maximum (default seven days). No new frontend payload or success DTO is required.

### Quota and billing boundaries

Guest daily generation allowance remains a rolling 24-hour ledger, default two starts. Admission rejection touches neither that ledger nor Geoapify reservations. Claim rejection before `start()` remains refundable; work crossing the existing provider boundary remains charged on failure, deadline or disconnect. No automatic refund was added after uncertain provider usage. Completed idempotency behavior remains behind account admission.

`geoapifyUsage.ts` and its authoritative durable credit reservations/settlement were not changed. Cancellation prevents a new fallback reservation; a known cancellation before fetch may release its unused reservation under existing rules. Sent/uncertain requests remain charged, and crash-held reservations remain durable. Existing credit accounting tests pass.

### Deployment boundary

The new gates require all replicas to share MongoDB and the same policy configuration. Separate Fastify app instances sharing only database state are exercised; independent operating-system API processes were not launched. No Redis, new package, indexes requiring migration scripts, or external job framework was introduced. Startup creates the admission TTL index explicitly.

The older auth/planning/guest-network Map limiters and public OSRM pacing remain process-local. Their allowances can multiply across replicas; they are supplemental, not the globally enforced generation/search gate. Existing rate-limit and provider pacing tests remain in the full API suite. Shared provider-wide public endpoint pacing still needs suitable deployment/egress coordination when adding replicas.

## Generation lifecycle

Each new claim contains `runId`, `startedAt` and `expiresAt`. Expiry is the admitted operation's deadline, not a fresh four minutes after destination recovery. Guest operation deadlines are additionally capped to the actual remaining stored activity lease minus one second, covering slow admission/database acquisition. Guest authority is never renewed or extended.

There are no heartbeats or infinite renewals. Work is protected throughout its bounded lifetime, including after two minutes. At expiry, another request can claim the trip with a new UUID. Legacy generating records without explicit expiry drain for four minutes from their old start time; missing legacy start time is recoverable. New claims always have explicit ownership and expiry.

Successful generation and generating-trip destination persistence require a live expiry and the current UUID. Generation completion and failure writes also compare expiry against MongoDB `$$NOW`; a lagging worker clock cannot authorize an expired commit. The completion retry read uses the same expiry guard, so expiration cannot masquerade as repeated expense conflicts. Failure marking requires the original UUID and start time; an expired worker cannot mark a newer run failed. Destination recovery cannot return a replacement run's token after losing its persistence race.

`generationContext` carries an AbortSignal and absolute deadline through async orchestration. It checks wall time as well as the signal, so a delayed timer cannot authorize writes. Client request abort or premature response socket close cancels work; a normal completed response does not. Requests already disconnected at handler entry are rejected. Timers/listeners are removed in idempotent cleanup.

AI transports combine caller cancellation, execution cancellation and their existing timeout. Overpass and OSRM transports, retries and pacing waits observe cancellation. Weather receives the execution signal. Geoapify fallback receives it without changing durable settlement semantics. Routing fallback rethrows overall cancellation but continues degrading on ordinary provider timeouts/unavailability. Stage boundaries and persistence recheck the operation.

Geocoding retains identical-query single-flight with independent subscribers. Cancelling one subscriber preserves another; the last departing subscriber aborts transport, whose five-second timeout remains in force. Promise rejection handlers are attached for late completion. Cancellation-owned attraction calls do not share the process pending-request cache with unrelated requests; existing per-trip attraction caching remains. Non-generation callers retain the existing process cache.

Errors: **504 / GENERATION_DEADLINE_EXCEEDED**, **499 / REQUEST_CANCELLED** (a disconnected client may never receive it), **409 / GENERATION_IN_PROGRESS**, and **409 / GENERATION_SUPERSEDED**. Normal validation, guest quota errors and provider-unavailable behavior retain their existing conventions. No broad error-contract refactor was performed. Internal generation metadata is excluded from existing DTO serialization.

## Remaining risks

- CPU clustering, scheduling, repair and quality routines are synchronous. They cooperate at stage/day boundaries, not inside every loop. A blocked event loop delays timer delivery; wall-time checks and MongoDB expiry still fence generation commits. External work cannot be retracted after a provider accepted it.
- A provider/mock that ignores AbortSignal may settle late. Handler cleanup waits for settlement; admission may expire and become recoverable, but the old generation is fenced. Actual fetch transports retain finite provider timeouts. In-flight MongoDB driver calls/transactions are not forcibly interrupted; a write already submitted can win a concurrent disconnect. No cancellation response is a promise to roll back an already committed write.
- Keep application and MongoDB clocks synchronized. Admission windows and recovery use application wall time; generation commits additionally check MongoDB time. A lagging worker cannot commit an expired generation, but severe clock skew can affect availability and admission fairness.
- Roll out compatible code/policy to all replicas together, or drain old workers before enabling mixed-version traffic. Old binaries do not understand new admission/expiry semantics. Guest support continues to require replica-set transactions from #22B.2; standalone deployments remain fail-closed.
- Long itineraries, congested providers or many routing stages can exhaust four minutes. They fail safely and remain retryable; no background queue, partial-result persistence or cancellation rollback was added. Observe real deployment traffic before tuning the two configurable request rates.
- Gates are per identity, not a new global workload cap. Account proliferation and aggregate egress capacity still depend on existing identity/ingress controls and durable provider budgets. Local auth/network/pacing mechanisms were not converted into distributed systems in this task.
- Existing guest-quota reservation crash behavior, broader error-contract work, unrelated mutation routes and other audit findings remain outside scope.
