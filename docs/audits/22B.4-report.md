## Investigation (before implementation)

The initial working tree contains extensive uncommitted API work and untracked audit files. These are preserved; no branch, commit or push is authorized.

- `queryClient.ts` disables focus refetch globally and gives queries a 60-second stale time. `useTrip` polls only `generating` trips (4 seconds); ready detail, lists and Budget have no recovery on focus. No cross-tab invalidation exists.
- Mutable detail includes itinerary/version, visits/visitRevision, pending automatic admission expenses and embedded budget/revision. Budget has its own query under `['trips', id, 'budget']`. Saved trips use filtered keys under `trips`. Candidates use `itinerary-candidates`; weather has explicit refresh mutations. Equipment also lives under `trips` but is outside this recovery scope.
- Budget is rendered by `TripBudgetCard` and queried by `useTripBudget`; there is no `BudgetPage.tsx` in this checkout. Budget GET checks only array/summary/revision presence; mutations trust generic assertions.
- TripPage consumes independent revisions for itinerary edits, visited-item locks and regeneration previews. Existing server conflicts and `mergeConfirmedTrip` protect independently advancing revisions. `cacheConfirmedTrip` cancels reads before committing responses. Budget compares revisions. Generation/confirmation directly set cache and invalidate lists; delete cancels/removes detail and invalidates lists. Visit results update detail and Budget, with transient expense feedback kept outside cache. Itinerary editing invalidates details/lists/candidates. Identity mutation callbacks are fenced by session identity; AuthProvider cancels/removes private caches on identity transitions and checks the session on focus/interval.
- `api/client.ts` parses JSON and casts to generic T. Detail, generation, confirmation, day apply/preview, edits and visits trust these casts. Shared Zod schemas cover analysis, attractions, weather, visit records and expense inputs, but most response envelopes are interfaces. Invalid JSON currently becomes null even for successful responses.
- Stable codes already include itinerary/idempotency conflicts and guest expiry/limits; HTTP status handles forbidden/not-found/conflict. Existing localized `invalid-response` mapping can report validation failures without payload details.
- main.tsx composes QueryClient, theme, auth and toast providers; App uses BrowserRouter/Routes. No render boundary exists, so an uncaught render failure removes the application. Existing loading/error components cover asynchronous query failures only.
- Existing tests use Vitest/jsdom, Testing Library and fetch/API module mocks. No web MSW dependency/infrastructure is installed; use the existing deterministic fetch mocks rather than introducing dependencies.

## Intended changes

Add lifecycle-managed, coalesced invalidation of active mutable trip/list/Budget queries on focus and payload-free cross-tab mutation notifications; defer recovery during mutations, consume abort signals and preserve revision merges. Add a narrowly scoped snapshot GET option because the existing detail GET triggers provider backfill: recovery must read authoritative state without provider calls. Validate high-value response boundaries with reusable existing schemas, preserving original successful payloads and optional legacy revisions. Add an outer localized render boundary with explicit retry and safe navigation. No AI assistant, attachment or backend domain rules change.

## Root causes and reproduction

The audit's three findings were confirmed by inspection before implementation. Deterministic regression coverage then exercised the reachable failures: a negative-control test retains the original disabled-focus configuration, invalidates without fetching, changes the server result and dispatches focus. The cached result remains old without recovery; installing recovery on that same client makes it converge. Two isolated QueryClients reproduce the independent-tab cache problem. Invalid trip/budget JSON is supplied at the real request boundary. A throwing React child demonstrates the missing render protection and explicit recovery.

An intermediate full frontend run exposed 41 failures in the existing TripPage fetch harness because it recognized only the exact old URL. After recognizing the snapshot query parameter, 17 existing visit tests still returned records missing the status timestamp required by the shared visit schema. The mock now supplies visitedAt/skippedAt, matching server behavior. All existing assertions were retained. An additional new test was corrected to count recovery requests separately from the initial mount request. These failures were resolved without relaxing validation or weakening tests.

## Cache and cross-tab design

- `TripRecovery` installs one lifecycle-managed recovery controller beneath QueryClientProvider. Global query defaults remain unchanged. Only trip lists, trip details and budget keys are targeted; catalog, equipment, packing, sharing and other queries are not refetched by this controller. Candidate queries are marked stale without launching discovery requests.
- Focus and visibility events coalesce for 100 ms, with a 10-second focus cooldown. Incoming mutation notifications also coalesce. Hidden tabs mark data stale and defer reads until visible. Inactive queries are invalidated but not fetched. There is no new polling interval; generation's existing polling remains intact.
- MutationCache notifications broadcast a constant `invalidate` string through `triply:mutable-data:v1`. No IDs, identities, tokens, expense information or trip contents are sent. Successful and failed mutation completions notify other tabs, since a failed acknowledgment may still represent a committed write. The signal is deliberately conservative across application mutations so authentication and guest migration also participate. Receivers do not rebroadcast reads, preventing echo storms.
- If BroadcastChannel is unavailable or cannot be constructed, a storage event with a random nonce is used. Both listeners and channel/timer/subscription resources are cleaned up, including StrictMode setup/cleanup. Restricted storage/channel environments retain focus recovery.
- Recovery checks the existing active session query before private reads, joins an in-flight session check, and reuses a check completed after the recovery signal. It stops when the identity changes; AuthProvider continues to own cache isolation and route transitions. Mutation-start cancellation suppresses earlier reads. Focus/cross-tab reads are deferred while any local mutation is pending, then resumed after completion.
- `useTrip` passes its AbortSignal to fetch. Reads with cached details use `?snapshot=true`, which skips weather/attraction enrichment in the existing owned GET route. Initial uncached reads retain current enrichment behavior. The backend change is confined to this read contract; ownership, legacy item identity recovery, concurrency validation and mutation logic remain intact. A dedicated route test verifies provider skips, normal-GET compatibility, authentication, ownership and deletion.
- Independent itinerary, visit and Budget revision guards remain authoritative. Generation and confirmation now use the existing cancel-and-merge helper too. Budget and Journey choose the newer revision between the dedicated Budget query and embedded detail snapshot, avoiding a slower Budget response masking newer automatic expenses. Existing preview-staleness checks react to refreshed itinerary versions; server conflicts still guard apply/edit operations. No client revision bypass was introduced.
- Deleted/malformed details produce existing controlled error UI and remove editing controls from the rendered page. Old valid query data is not replaced with malformed payloads. Server owner filters handle transferred trips; session transitions retain the existing private-cache cleanup.

## Runtime validation scope

`request` and `parseResponse` accept a Zod schema tied to their TypeScript return type. Successful JSON is validated before entering trusted query/mutation state. The original JSON is returned after validation, preserving wire shapes and avoiding insertion of Zod defaults or transformations. Invalid responses raise `ApiError` with status 502 and stable `invalid-response`; existing EN/PL error mapping displays controlled copy. Error details contain only that code, not the rejected payload or Zod diagnostics. Existing non-success HTTP codes and session-expiry behavior remain supported.

Validated boundaries: trip lists/details, analysis/requirements, confirmation, generation, itinerary edit responses, day regeneration preview/apply, visit transitions/automatic-expense retry, and Budget GET/create/update/delete/allocation responses. Detail validation includes nested days, activities, map stops/geometry/segments, visit timestamps, revisions, expense provenance and Budget summaries. Expense IDs must be unique. Detail/edit/visit/apply responses must match the requested trip; previews must match the requested trip and day.

Shared schemas are reused for analysis, locations, status, equipment, weather availability, visit progress, admission, money, currencies, expense inputs/allocations and regeneration preferences. Small response envelopes live in the frontend because these shared contracts were interfaces, not compatible response schemas. Shared source and dependencies are unchanged. Optional legacy itinerary/visit revisions and absent occurrence IDs remain accepted; current visit records must match their shared timestamp contract. Unrecognized metadata remains preserved. This is structural validation, not recomputation of server totals or business rules.

Unrelated endpoints (including candidates, explicit weather-refresh envelopes, profile, Saved, packing and the disabled Assistant) retain their existing handling. Optional quality/admission-summary metadata and optional itinerary diagnostic extensions are not exhaustively validated. This report does not claim application-wide elimination of generic API assertions.

## Render boundary

`AppErrorBoundary` wraps theme, auth, toast, router and route views, beneath the persistent QueryClientProvider. It catches unexpected descendant rendering/lifecycle errors and displays localized EN/PL fallback copy using native controls that do not depend on the failed theme/router. No exception text or stack is rendered. Retry remounts the application at its current URL only after a click. A second failure returns to the fallback, without an automatic retry loop. Home provides a safe full navigation. Query cache and cookie-backed session survive a retry; in-memory unsaved component drafts may be lost when a crashed subtree is remounted. Async/event-handler failures remain the responsibility of existing error handling.

## Remaining risks

- Recovery is bounded eventual consistency. Hidden tabs defer reads; very rapid repeated focus events can be suppressed for up to ten seconds, and unsupported/blocked messaging falls back to the next eligible focus. There is no continuous remote push from server-only writes; returning to the tab revalidates.
- The payload-free signal intentionally revalidates all active mutable trip queries in the receiving tab rather than exposing a specific trip/identity. Unrelated mutation completions can therefore cause a small conservative extra snapshot/Budget read, but not provider discovery or indiscriminate application-query refetches.
- Runtime schemas cover the mutable boundaries described above, not every endpoint or diagnostic metadata field. They establish structure, currency/money constraints and identities, not semantic equality of server-computed totals.
- Render retry retains cache and session but remounts local UI state. Persistent failures need navigation; event-handler/async errors are not React render-boundary errors.
- The full frontend build still has the pre-existing large initial bundle warning. No delivery redesign or dependency upgrade was included.
