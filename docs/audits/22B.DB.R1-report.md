## Exact root cause

The original successful MongoDB response serialized `lockCount` as a BSON Long-shaped object:

```json
{"ok":1,"lockCount":{"high":0,"low":1,"unsigned":false}}
```

The operator used `assert.equal(locked.lockCount, 1)`, comparing an object to a JavaScript number. That assertion failed before the locked manifest or `mongodump`. The `finally` block issued the matching unlock successfully, then repeated the same mistake with expected counter 0. Throwing from `finally` replaced the original exception, so the recorded stack showed the cleanup assertion rather than the first failure.

The original incident responses are unchanged and preserved again as `r1-before-phase-b-lock.json` and `r1-before-phase-b-unlock.json`. Tests load those actual JSON files rather than reconstructing their response shape from memory.

### `phase-b-lock-safety.ts` — new pure safety module

- `lockCounter(unknown)` accepts only a nonnegative safe-integer JSON number or the exact `{high,low,unsigned}` representation. Both 32-bit words must be signed 32-bit integers and `unsigned` must be boolean. It reconstructs all 64 bits with `bigint`, applies signed interpretation when required, and rejects negative or greater-than-`Number.MAX_SAFE_INTEGER` results without rounding.
- Missing fields, extra fields, arrays, strings, booleans, fractional words, invalid word ranges, non-finite/unsafe numbers, negative zero and unrecognized encodings are rejected. Extended JSON `$numberLong` and direct JavaScript bigint input are deliberately unsupported and fail closed; neither was an incident response format.
- `verifyCounter` requires exact `ok:1` and exact counter **1n for acquisition**, **0n for release**. Recognizing a positive counter such as 2 does not make it acceptable.
- `withOwnedSnapshot` executes cleanup assessment in `finally` whenever a lock command may have been attempted. Ownership is established only by a successful exact counter-1 response after independently observing the same original instance unlocked.
- A transport failure, malformed response or unexpected counter leaves acquisition ambiguous. Cleanup assessment then refuses to issue an unlock and reports manual intervention. It never assumes an unverified response establishes ownership, and never proceeds to backup work.
- Instance checks cover full container ID, start time, image ID, both source volume identities, MongoDB `hello.topologyVersion.processId` and expected lock state. The generated shell guard also verifies the process identity and lock state in the same shell invocation that would issue a command. Docker execution targets the full original container ID, avoiding a container-name replacement race.
- `SnapshotFailure` retains the original thrown value as `primary` and `cause`, with a separate `cleanup` value and explicit presence flags. If only cleanup fails, that failure is reported. A cleanup failure cannot replace an existing primary failure.
- Review gates block every disruptive stage and acceptance execution. There is no command-line flag that bypasses these holds. The remaining read-only preflight path still requires an explicit maintenance invocation, and its evidence-collision issues remain documented below.

MongoDB does not supply a per-operator fsync-lock ownership token. The safety module's ownership claim is therefore a verified unlocked-to-counter-1 transition within an exclusive maintenance operation, bound to a specific original instance. It is not proof against an independent administrator concurrently changing the global lock. Exclusive operator control remains a resume prerequisite. Ambiguous acquisition requires manual assessment rather than speculative cleanup.

### `phase-b-operations.ts` — repaired integration

The snapshot branch delegates to the new state machine. It validates the running original and process identity, uses same-invocation shell guards, records the validated acquisition before backup work, and records unlock only after counter and released-state verification. Evidence filename collisions are checked before acquiring a lock. Proposed future lock/unlock evidence uses `r1-resume-*`, preserving incident files; no such resume evidence was created in R1.

The outer failure handler serializes primary and cleanup errors separately and sets exit code 1 before writing failure evidence. Failure-log write errors are caught and reported separately. Original backup/restore assertions were not relaxed or bypassed.

An important observed serialization detail was checked read-only: on this unlocked MongoDB 7 instance, successful `currentOp()` returned `{inprog:...,ok:1}` without a `fsyncLock` field. The adapter accepts that observed unlocked representation only with a valid successful command and operation array. An explicitly present non-boolean lock field is rejected. Process identity is normalized explicitly with `toString()`; unknown lock-counter representations are not normalized to zero.

## Review of remaining unexecuted code

These issues were found by source review. They were not exercised on the live database and are not bypassed by this repair. Hard review holds keep the affected code unreachable.

1. **Snapshot deadline is not independently enforced.** The legacy script checks 180 seconds after snapshot work. Individual `spawnSync` timeouts and `finally` do not provide a guaranteed independent unlock path if the operator dies or blocks, and killing a Docker CLI does not prove its container-side command stopped. A bounded design must preserve lock ownership/identity rules and test deadline/failure paths before enabling live snapshots.
2. **Fresh quiescence is partly external to the script.** The earlier PowerShell wrapper checked host processes, listeners, clients and scheduled tasks/services. The logical branch alone only samples MongoDB clients and filters a particular mongosh app name. Another manual shell could be hidden by that broad name filter. Resume must identify inspection connections explicitly and reject every other client, while freshly checking host writers and runner parents.
3. **Evidence is not yet a durable, attempt-bound state machine.** Preflight still targets historical filenames and will collide safely. Later phases load old `passed:true` evidence without binding it to the current snapshot, archive hashes, container lifecycle and same maintenance attempt. Cold archives are hashed at creation but not rehashed immediately before extraction. Review must ensure stale artifacts cannot authorize stopping/replacing the original. Hashes and manifests must remain mandatory; no gate was removed.
4. **Failure cleanup for isolated checks needs ownership guards.** Restore/clone verification lacks an encompassing owned-container cleanup path on failure. A failed check can leave a temporary MongoDB running with clone/restore mounts. Cleanup must stop only the recorded owned instance, preserve volumes and retain both primary and cleanup failures. The successful-path native-command helper checks exit codes, but log-write errors can still obscure native failure detail outside the repaired snapshot handler; readiness polling should also record transport errors/signals distinctly.
5. **Restore verification needs all intended namespaces.** The current canonical utility verifies the 12 `triply` collections. The full logical archive also contains system metadata outside that database. Independent restoration must inventory expected databases/collections and explicitly account for system/local/TTL differences, not infer those from a Triply-only digest match. Its index/options/content assertions should remain strict.
6. **Cutover and acceptance are not an atomic gated progression.** Original-container removal and Compose startup have no complete evidence-bound recovery/freeze controller. Failures before versus after clone divergence need the reviewed distinct handling; no automatic return to stale originals is permissible. No such recovery action was attempted here.
7. **Acceptance cleanup and evidence require repair.** The stale-writer `finally` can mask the primary assertion with a rejected pending request. An app-close failure can skip disconnect/evidence saving; waiting for the pending request has no hard bound. The divergence marker and acceptance result use overwriting file writes, and the marker is emitted before connection/first-write checks. Provider guards are present, but the harness has never run; they are not live-provider safety evidence. These issues require deterministic, provider-blocked tests before enabling the entrypoint.
8. **Application reopening remains separately gated.** Ordinary `startServer()` calls destination seeding before app initialization. No normal startup is approved by this repair. A compatible no-unrelated-seeding runtime path and current #22B/F-01 build verification must be reviewed before reopening traffic.
