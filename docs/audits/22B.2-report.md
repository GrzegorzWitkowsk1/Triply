## Root cause and investigation

1. Guest identity is a random 16-byte hex ID in a signed, MongoDB-backed guest session. Session secrets are distinct from owner IDs. Services receive the existing `guest:<id>` tagged owner. Trips use `guestId`, `user: null` and a unique guest storage slot; Saved items use `ownerType: guest`, `ownerId: <id>`.
2. The existing route allowlist in `middleware/tripIdentity.ts` acquires activity in `preHandler`, after session validation and before the handler. Account authentication remains unchanged. The requested `services/tripIdentity.ts` does not exist; identity helpers actually live in `middleware/tripIdentity.ts`.
3. Previously acquisition atomically appended a bare random request ID to `guest_handoffs.activeRequests`, conditional on handoff state `active`.
4. Handler `finally` and `onSend` removed the ID. Neither hook can run after process termination.
5. Sign-in moves the handoff from `active` to `pending`, binding it to the authenticated user, replacement session hash and a random context ID. New guest acquisitions are rejected. Migration originally treated **any** activity ID as busy forever.
6. Confirmation uses a snapshot/majority MongoDB transaction: check the bound pending context and activity, write `completed` to the handoff, transfer ownership of trips, transfer/merge both Saved collections, and persist the exact receipt. Native collection updates deliberately bypass immutable owner fields only in this authorized transaction.
7. All trip ownership changes, Saved copies/merges/deletions and receipt changes remain in that transaction. Guest quota records are deliberately retained under the guest identity; they are not transferred or duplicated.
8. Already admitted operations can continue after sign-in enters `pending`. They previously relied on migration waiting for every marker. Most resource updates additionally scoped ownership, but document saves, new drafts, Saved upserts, and a weather availability update showed why owner-scoped queries alone were insufficient as a complete fence.
9. A crash leaves the bare marker indefinitely. Whole-handoff TTL cleanup is 30 days, much longer than the 15-minute import context, and does not provide useful request recovery.
10. Existing handoffs, quotas, generation claims, ownership queries and migration use MongoDB state. The new safety mechanism supports multiple API instances; no process-local lock is required. Separate Fastify app instances sharing MongoDB are tested, but independent OS processes are not launched by the new tests.

The old invariant was “migration cannot transfer ownership while any admitted guest request remains.” Permanent markers preserved safety at the expense of liveness. Simply expiring them would discard that invariant without protecting every write.

## Safety model

- **Lease identity:** guest ID plus an unguessable UUID per admitted request. The existing request-local `{ guestId, id }` representation stays internal. Persistent entries now contain `{ id, expiresAt }`.
- **Lifetime:** five minutes from atomic acquisition. There is no renewal, heartbeat, or automatic extension. This is a bounded write-authority lifetime, not an assertion that a process has died and not a forced cancellation of provider work.
- **Acquisition:** conditional single-document `$push` while state is `active`, retaining the existing 30-day handoff cleanup policy. Multiple requests get independent IDs.
- **Release:** atomic `$pull` by the exact lease ID. Repeated release is harmless; an old release cannot remove a different, newer lease.
- **Recovery:** before pending status/confirmation, an atomic aggregation update converts legacy strings once into leases with a five-minute drain deadline and filters expired entries. Subsequent observers cannot extend that deadline. No TTL scheduler, completion hook, manual deletion, or background cleanup process is needed for recovery.
- **Durable write barrier:** `guestWrite` validates the exact lease, its expiration and state (`active` or `pending`) and increments `writeRevision` on the handoff **in the same transaction and session as the resource write**. It uses Mongoose's transaction wrapper so document save state is restored on transaction retries. An epoch check at request start is unnecessary: every commit writes the shared durable fence.
- **Request context:** AsyncLocalStorage carries the admitted lease into service calls and delayed callbacks. It conveys identity only; it is not the lock or the authorization decision. The database transaction provides both.
- **Migration:** continues to require an empty recovered activity array and updates that same handoff inside its existing ownership-transfer/receipt transaction. A valid lease still yields the existing busy `409`. Pending sign-in prevents new acquisition, but an already admitted, unexpired request may finish before import.
- **Expiry/failure:** no lease renewal is attempted. A request whose lease expired, was released, or was fenced cannot make further resource writes. A new active request gets a different lease and cannot revive the old one. Database failure never triggers an unfenced fallback write.
- **Provider boundaries:** external work stays outside transactions. Each short persistence operation explicitly receives its transaction session, including the native packing update.

### Commit-order proof

Both a guest resource write and migration must write the same handoff document transactionally. MongoDB therefore serializes them or aborts/retries a conflicting transaction:

1. If the guest transaction wins, its resource change commits before ownership transfer. Migration then transfers the resulting current resource.
2. If recovery/migration wins, a fresh guest transaction cannot match its expired/missing lease or completed handoff. If the guest transaction used an earlier snapshot, its fence update conflicts; on retry it checks current durable authority and fails.
3. If a request pauses **after** validating its lease inside the transaction, migration still cannot commit past its handoff write. Expiration during that transaction does not permit migration to overtake the resource write.

Thus an old request cannot commit a resource mutation after transfer, even when the resource query itself uses only `_id`. The delayed-writer tests deliberately exercise that weaker predicate to verify the transaction barrier independently of existing owner filters. All existing owner filters remain; the weather availability update also gains the missing owner predicate.

Explicit exceptions: migration writes already use their own transaction; Assistant writes are account-only via the existing guest allowlist; catalog seeds are not guest routes. Guest quota ledger finalization, provider usage accounting, MongoDB session storage and packing generation coordination leases do not transfer ownership and remain under their existing policies. In particular, a charged guest operation can still be marked failed after losing authority without refunding its provider usage. None of those writes can mutate an imported trip or Saved account resource.

## Stable failure behavior

| Condition | Outcome |
| --- | --- |
| New guest request after sign-in begins | Existing retired-session behavior, normally `401`; acquisition races retain the existing `409` sign-in message |
| New guest request after completed import | Retired guest session rejected; completed handoff cannot acquire a lease |
| Existing request loses its lease | Resource persistence rejects with exposed `409`, instructing refresh; no resource mutation |
| Migration sees valid activity | Existing `409` busy response |
| Migration sees expired/orphaned activity | Recover atomically, then use the unchanged import transaction |
| MongoDB unavailable at the write barrier | Exposed `503`, no unfenced fallback; later cleanup/recovery remains idempotent |
| Standalone MongoDB | Guest resource writes fail closed with `503`; migration retains existing safe `503` refusal |
| Process dies during import | MongoDB commits the entire transaction/receipt or aborts it; retry observes completed receipt or retries pending context |
| Lost HTTP response | Confirmation reconciles the durable receipt and returns `alreadyImported: true` |

No lease IDs, session secrets, or guest tokens are included in new public errors or logs. Existing ownership, session expiration, quota limits and accounting remain unchanged. The five-minute non-renewable lifetime means a very slow guest operation must refresh/retry instead of retaining write authority indefinitely.

## Remaining risks and deployment assumptions

- **Replica-set MongoDB is now required for guest resource writes, as it already was for migration.** Standalone guest mutation refusal is deliberate and tested. No fallback can safely separate lease validation from insertion/upsert or an unscoped document save.
- **Coordinated rollout is required from the old implementation:** stop/drain every old API binary before enabling recovery on upgraded instances. A paused old binary has no transactional write barrier; new code cannot retrofit fencing into its writes. The legacy drain period bounds orphan recovery only after all running writers use the new fence. Mixed versions are not claimed safe.
- New restart tests simulate abandoned requests and instantiate fresh Fastify apps against the same MongoDB state. They do **not** kill an OS process, restart MongoDB, test network partitions, or run independent API processes. Transaction rollback/retry and durable receipt tests cover the corresponding database outcomes, not a literal process-kill experiment.
- No known guest resource persistence path remains unfenced in the current route/service inventory. Future background jobs, aliases or new collections must explicitly retain the same transactional barrier. Internal test/setup calls outside an admitted request intentionally have no request context; they are not public guest entry points.
- Application clock skew can shorten or lengthen the effective admission lifetime, but it cannot bypass the shared transactional fence. Availability still depends on MongoDB becoming reachable and on eventual transaction completion/abort.
- Provider work is not forcibly canceled at expiry. Its result can be discarded; previously charged usage is not refunded. Pending admission receipts are embedded in trips and transfer atomically, so an account can recover unfinished expense posting through the existing retry flow.
