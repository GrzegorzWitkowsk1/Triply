## Root causes and baseline reproduction

`routes/health.ts` always sent HTTP 200 and `status: "ok"`. It reported Mongoose connection state in a separate `db` field, which an HTTP-only probe would ignore. Connection state alone also cannot distinguish a writable transactional deployment from a standalone or unavailable primary. Session hooks could access MongoDB before the health handler when a signed cookie was supplied; the response compatibility hook could turn a deterministic successful body into HTTP 304.

Before changing implementation, `bun run vitest run src/routes/health.test.ts` failed its disconnected-database assertion: expected **503**, received **200**. The test owns a Fastify instance with no MongoDB connection. An initial sandboxed invocation failed to load Vitest configuration; the approved invocation produced the actual reproduction.

Compose published `27018:27018` without a host IP. Baseline `docker compose config` confirmed the effective port entry had no `host_ip`. Read-only `docker ps` additionally showed the existing `triply-mongo` container publishing `0.0.0.0:27018->27017/tcp` and `[::]:27018->27017/tcp`.

Importantly, that running container differs from repository configuration: `docker inspect` reported command `["mongod"]`, container port 27017, and the existing `triply_mongo_data` volume. Read-only `db.hello()` / `rs.status()` inspection returned **NoReplicationEnabled**. It is a standalone and cannot provide the transactions required by current guest operations. This pre-existing runtime drift was not repaired by changing existing data or containers.

## Health contract

| Endpoint | Meaning | Status and deterministic body |
| --- | --- | --- |
| `GET /health` (also HEAD) | Readiness for the current replica-set application topology | **200** `{"status":"ok","db":"connected"}` when usable; otherwise **503** `{"status":"unavailable","db":"disconnected"}`. |
| `GET /health/live` (also HEAD) | Process can respond independently of database availability | **200** `{"status":"ok"}` while the HTTP server accepts requests. |

Both endpoints set `Cache-Control: no-store`, bypass session reads/writes even with a valid signed cookie, and bypass ETag/conditional-304 conversion. Security and CORS behavior remains in place. No credentials, hostnames, URI, exception details or topology diagnostics are returned. Removed changing uptime/timestamp and package metadata to keep the response small and deterministic. The `db` field describes dependency readiness, rather than merely the driver's connected flag.

Readiness requires Mongoose state **1**, an initialized database handle, and a successful `hello` command selected with `readPreference: "primary"`. The reply must report `ok: 1`, `isWritablePrimary: true`, a replica-set name, logical sessions and no read-only flag. A standalone can answer ping successfully yet fails this check. During primary loss/election or server selection failure, errors/timeouts return 503. A fresh successful check returns 200 after recovery.

The MongoDB driver operation has **900 ms** `timeoutMS` for selection/execution. An independent **1,000 ms** deadline returns false and aborts the command, also bounding a transport that ignores its own timeout. Concurrent requests share one command per app. There is no successful-result cache or background polling, so a prior 200 cannot hide a subsequent failed probe. If a transport ignores cancellation, probes retain the failed in-flight result until it settles rather than accumulating operations. Late success cannot change an already returned 503.

`hello` is cheap metadata, not an application query or a transaction/write per probe. Sequential probes issue one command each; use ordinary seconds-scale probe intervals. This checks current primary/topology usability, not every collection permission, disk/quota condition, majority write acknowledgment or a guarantee that the next request cannot race a later outage. Real transactional regressions separately verify the application's required operations. Timers depend on the event loop; no HTTP handler can promise a hard wall-clock deadline under a blocked process.

The `preClose` hook flips readiness before draining. An already-running probe rechecks the shutdown flag after awaiting MongoDB, so it cannot return 200 after shutdown starts. Once Fastify stops accepting requests, probes may fail at the transport rather than receive JSON.

## MongoDB security and topology compatibility

The only Compose edit is **`127.0.0.1:27018:27018`**. Effective `docker compose config --format json` confirms `host_ip: "127.0.0.1"`, `published: "27018"`, `target: 27018`, protocol TCP. Container command, initialization healthcheck, restart policy, network and volume mounts are preserved. `--bind_ip_all` remains necessary for host forwarding/container networking; restricting host publishing is the security boundary addressed here.

The configured replica member advertises `127.0.0.1:27018`. Matching host/container ports allow the MongoDB container itself and the host API to reach that address in their respective network namespaces. Host-loopback publishing does not change discovery or transaction semantics. No `directConnection=true` workaround was added. Disposable Windows-host MongoDB tests use ordinary replica-set discovery and commit real transactions.

Another application container would resolve its own loopback to itself, so this existing advertised topology is not suitable for an API container in a different namespace. There are currently no such Compose clients. Moving the API into Docker would require deliberately designed member addresses reachable by every client, outside this task.

**Configuration validation is not runtime activation.** The existing container still uses its old public publishing and standalone topology. No container was recreated, stopped, reset or migrated; no persistent database or volume was deleted. Applying the port mapping requires authorized operational replacement of that container while preserving its data. Reconciling its standalone topology also needs a separately reviewed, data-preserving operational plan. This report does not claim either action occurred.

## Deployment considerations

Use `/health` for load-balancer readiness and startup gating. Playwright already uses this path and no CI/probe URL change is needed. Use `/health/live` for process liveness/restart policies so a database outage does not cause an API restart loop. Configure external probe timeouts above one second to allow the API to return its bounded 503. Actual production probe definitions are not in this repository and were not altered.

The current readiness contract targets the repository's replica-set topology. Standalone MongoDB deliberately fails readiness because required guest transactions cannot run there. A future sharded/mongos deployment would need a compatible topology check; no such deployment is configured or claimed verified here. Startup connection/index work retains existing driver timeouts before listening; the one-second bound applies to health probes, not the entire startup sequence.

Existing local URI defaults and env files remain unchanged. If an existing replica-set configuration advertises other addresses, the healthcheck intentionally does not reconfigure it; an operator must inspect whether those addresses are reachable before applying a new publishing configuration. Unauthenticated local Compose MongoDB is development-only and must not substitute for secured production infrastructure.

## Remaining risks

- The inspected persistent container remains publicly published and standalone until an authorized operational change. Therefore runtime acceptance on that existing container is outstanding even though repository configuration and isolated regressions pass.
- No new Docker container was created and the existing container was not replaced. Loopback-only **effective configuration** was verified, not newly activated Docker port forwarding or a LAN reachability experiment.
- Real transactions ran in disposable native MongoDB replica sets on Windows, not in the existing standalone Docker container. No persistent database was reset, migrated or recreated.
- Controlled topology replies cover election failure semantics; an actual multi-node election, network partition, disk exhaustion and production traffic were not induced.
- Metadata readiness is a bounded point-in-time signal with the practical limits described above. A future mongos topology would need an explicit extension.
